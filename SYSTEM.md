# Fireweed

Fireweed is a local, language-agnostic Go CLI for checked spec-driven development and regeneration. The unchanged fireweed-design-v1.md is product authority; docs/rebuild/GOAL.md is the restart prompt and ACCEPTANCE.md defines ordered milestones and gates, adding no product scope. Bootstrap supplied pre-cutover workflow control and one CLI smoke comparison; it remains an explicit recovery option, never implementation input or a product dependency. Record relevant discrepancies briefly in docs/rebuild/DECISIONS.md; add evals only for uncovered design behavior.

## Modules

contracts owns public data, Markdown grammar, IDs, hashes and zones. gitstore owns safe local Git and process primitives. assets owns embedded recipes, playbooks and versions. project owns discovery, projection, validation and authoring. checks owns JUnit coverage, hooks, boundaries, history and doctor. workflow owns claims, lifecycle, provenance and context. runner owns agents, queues, retries, recovery and drills. app composes the CLI. SPEC.md frontmatter is the only graph source.

## Author and worker policy

An authorized execution goal permits local authoring and commits, including execution on main; it does not assert human merge approval. Planning alone authorizes no product execution. Keep normal approval enforcement intact. Authors edit protected setup/infrastructure/evidence between active changes and commit separately. Only fireweed applies Specs/Decisions, phase commits and archives. Workers obey context/zones, never commit, weaken enforcement or edit protected planning/design/tooling. Workers must not invoke lifecycle mutators (including start, done, release, next, run or abandon), edit run/phase fields or Provenance, or advance phases themselves; they verify and return to the outside owning controller. Audit stays enabled with separate restricted context. Regeneration receives retained contracts, evals and allowed dependency interfaces, without old implementation/history/bootstrap. Push only under explicit owner authorization recorded in PROGRESS.md; no publication or release tags.

## Scope guardrails

These rules bound GOAL.md and ACCEPTANCE.md. The next planned milestone is checks contracts and proof (CK1–CK4), in ACCEPTANCE's order; execution awaits owner authorization. Full product completion remains open. PROGRESS holds current state and the controller pin; DECISIONS retains design clarifications. Completed procedures and historical lessons remain in git history, not the execution queue.

- **Scope and stops.** Implement only an owner request, demonstrated failure or concrete unmet design/spec clause within the selected milestone. Agent suggestions and drill gaps authorize no extra work. Stop on a blocked change, independence/access failure, an unresolved correction or a decision needing the owner. Each owner-selected milestone states a budget (changes or days); when it is reached, stop for owner review. Stop after the selected work even if budget remains. No push is authorized for this milestone.
- **Reconstruction inputs.** Never use `rebuild-v1`, bootstrap source/tests or deleted code as implementation oracles; old spec IDs have no authority. Regeneration also excludes old implementation/history, binaries, saved attempts and dependency internals. Supply retained contracts/evals and permitted dependency interfaces; keep full verification implementations outside worker inputs.
- **Conventions.** The product never contacts the network or runs fetch/push. Read commands run no hooks/agents and change no files, index or refs; output is deterministic. Check these by review and one app-level PATH-shim eval recording Git/hook/agent invocations, not module specs.
- **Evals.** Use plain Go public-interface tests, temporary repositories, fixture hooks and fake agents. Inject faults through public inputs. No process instrumentation: cgo, syscall/I/O interposers, loader tricks, sandbox profiles, re-signed tools, argv-classifying Git proxies, fsmonitor traps or byte-coverage observers.
- **Specs.** One observable behavior per item, at most three normative clauses and about 80 words. Do not bundle independent behaviors; punctuation or input lists alone do not require splits. No aliasing, backing-storage, purity or syscall requirements. Fix authored or identified violations, without repeated whole-repository rewrites.
- **Environment and processes.** Support macOS/Linux on amd64/arm64 with ordinary full SHA-1 clones. Windows, other architectures, SHA-256/partial/promisor clones, replacement refs, fsmonitor and filters get no special code/evals. Set GIT_NO_LAZY_FETCH and disable optional Git callbacks where convenient. Hooks/agents have timeouts and process groups; cancellation kills the group. Escaped/daemonized/reparented processes are a documented limit. No native objects, assembly, cgo or embedded/generated architecture binaries.
- **Cost and corrections.** Own Verify stays under five minutes, full implementation Verify under 25; aim for at most 15 cases per spec. Reuse representative assertions; split changes or remove redundancy while preserving obligations. Do not raise bounds or add instrumentation. After two unsuccessful corrections of one issue, try one simpler scoped approach; if unresolved, report and stop. Renaming the issue resets nothing.
- **Audit.** Keep independent restricted auditing, normalized clause quotes and visible rejection diagnostics. Findings identify spec clauses with no asserting test, not helpers, observer calibration, platforms, unnamed edge cases or conventions. Re-audit only IDs with previous findings. At most two persisted findings round trips; further/untestable findings become Questions and block/release, then stop. No replacement change to reset rounds.
- **Authoring.** Read the author-change playbook and projected specs; run context before each step and verify with the controller. Motivation names a design/SYSTEM clause or user need. Prefer authorized narrowing with legitimate already_satisfied over extra hardening. No manual Spec/Decision edits. Batch coherent work by module with no cap on affected IDs; keep specs atomic. Splits/retargeting preserve every obligation/assertion and behavior/interface. D006 migrations cover existing error paths, eval corrections and emitted-code explanations only. Preserve normal fail-first, frozen phases and audits. Frozen-eval corrections use audited eval_fix, preserve coverage and pass all own evals; the controller's capabilities govern.
- **Enforcement.** P07 and audit bounds remain active, alongside the milestone budget; a repeated-module warning is no separate stop. Read live unapproved counts from status --json and limits from fireweed.yaml; record neither here. Never alter refs, bounds or requirements to evade checks. Process notes belong in PROGRESS, not module Decisions.
- **Decisions.** Record only missing behavioral choices in one or two sentences; keep module Decisions under about 300 words. Remove superseded choices through Removed decisions. Fixture, verification and recovery notes belong in change Notes or PROGRESS.
- **Evidence.** Evidence is only what is committed: archived change files with their Provenance, and drill reports in .fireweed/drills/. Temporary clones, /tmp paths, hash manifests, case counts and binary hashes, other than the single controller pin, are not recorded in planning documents.
- **Acceptance.** Review milestone scope once, then only affected fixes. Preserve committed archives/reports and required proof refs; update PROGRESS only for state, next work or standing rules. Reuse valid checks/proofs; required phase verification still runs. Explain warnings or fix them within scope, without speculative cleanup. Stop verification when applicable gates pass unless relevant changes or unresolved failures invalidate evidence. Drill gaps need owner agreement before fixes. Every full-completion gate remains required later.
