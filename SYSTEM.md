# Fireweed

Fireweed is a local, language-agnostic Go CLI for checked spec-driven development and regeneration. The unchanged fireweed-design-v1.md is product authority; docs/rebuild/GOAL.md, PLAN.md and ACCEPTANCE.md define execution and gates, adding no product scope. Bootstrap supplies workflow control and one CLI smoke comparison, never implementation inputs or product dependencies. Record relevant discrepancies briefly in docs/rebuild/DECISIONS.md; add evals only for uncovered design behavior.

## Modules

contracts owns public data, Markdown grammar, IDs, hashes and zones. gitstore owns safe local Git and process primitives. assets owns embedded recipes, playbooks and versions. project owns discovery, projection, validation and authoring. checks owns JUnit coverage, hooks, boundaries, history and doctor. workflow owns claims, lifecycle, provenance and context. runner owns agents, queues, retries, recovery and drills. app composes the CLI. SPEC.md frontmatter is the only graph source.

## Conventions

Module path: github.com/lurkshark/fireweed. Thin api.go facades and public contracts are retained interfaces; all behavior belongs under internal/. Evals import public packages only and use temporary repositories, explicit fixture Git identities, deterministic local hooks and bounded fake agents. No runtime network calls, bootstrap delegation, or private implementation tests. Keep dependencies minimal (YAML parser only initially). Never import a public parent from its own internal implementation; shared data belongs in contracts.

## Author and worker policy

The goal authorizes local authoring and commits, including execution on main; it does not assert human merge approval. Keep normal approval enforcement intact. Authors edit protected setup/infrastructure/evidence between active changes and commit separately. Only fireweed applies Specs/Decisions, phase commits and archives. Workers obey context/zones, never commit, weaken enforcement or edit protected planning/design/tooling. Audit stays enabled with separate restricted context. Regeneration receives retained contracts, evals and allowed dependency interfaces, without old implementation/history/bootstrap. Push only under explicit owner authorization recorded in PROGRESS.md; no publication or release tags.

## Scope guardrails

Added after the 2026-10-26 restart; tightened 2026-10-27. These rules override broader readings of GOAL.md, PLAN.md and ACCEPTANCE.md. Bootstrap 0.1.1 supplies the revised audit, eval_fix and unapproved-work bounds, including whitespace-normalized audit quotes, visible rejection diagnostics and restricted automatic auditor inputs. PROGRESS.md records verified setup, current state and the next slice; archived changes hold per-change evidence in their Provenance. LESSONS.md is bounded historical input.

- **Priority.** First prove one manual lifecycle through NEW, building only needed dependencies and wiring app promptly. Then complete init/doctor, bounded next/run and the remaining surface. GOAL.md and PLAN.md define exits; module order does not require finishing whole libraries first. Resume the agreed next slice from PROGRESS.md. Before authoring, name the CLI scenario and missing behavior in the existing Motivation; return from a dependency to its caller as soon as usable, and close the slice with an actual NEW invocation and inspectable result. Additional work needs an unmet design/spec clause, demonstrated failure or explicit human request; theoretical probes, stylistic discomfort and agent suggestions alone are insufficient.
- **Reference branch.** Use LESSONS.md as bounded history. Never consult `rebuild-v1`, bootstrap source/tests or deleted code as implementation oracles; old spec IDs have no authority. Regeneration also excludes old binaries and saved attempts.
- **Conventions are not specs.** Locality and safety properties are project conventions checked by review: the product never contacts the network or runs fetch or push; read commands never run hooks or agents and never change files, the index or refs; output is deterministic. Do not restate them in module specs. Their only eval is one app-level test that runs read commands with a PATH shim recording git, hook and agent invocations.
- **No process-level instrumentation in evals.** Evals are plain Go tests over temporary repositories, fixture hooks and fake agents. No cgo, I/O or syscall interposers, dynamic-loader tricks, sandbox profiles, re-signed tools, Git proxies that classify argv, fsmonitor traps or byte-coverage observers. Faults are injected through public inputs and fixture repositories.
- **Spec shape.** Each item states one observable interface behavior in at most three normative clauses and about 80 words. Do not bundle independent behaviors with slashes or commas; punctuation or a list of inputs for one behavior does not itself require a split. No aliasing, backing-storage, purity or syscall requirements. Apply this to authored specs and identified violations; do not launch repeated repository-wide rewrites. Preserve explicitly authorized split work in PROGRESS.md.
- **Supported environment.** macOS and Linux on amd64 and arm64, with ordinary full SHA-1 Git clones. Windows, other architectures, SHA-256 repositories, partial or promisor clones, replacement refs, fsmonitor and content filters are not supported and get no specific code or evals; set GIT_NO_LAZY_FETCH and disable optional Git callbacks where convenient and stop there.
- **Process control.** Hooks and agents run in their own process group with a timeout. Cancellation kills that group. Processes that leave it (setsid, daemonizing, reparenting) are a documented limitation. Product code contains no native objects, assembly, cgo, embedded executables or generated per-architecture binaries.
- **Eval cost.** Keep own Verify under 5 minutes and full implementation Verify under 15; aim for at most 15 cases per spec. Reuse fixtures and representative assertions. If needed, split the change or remove redundant cases while preserving design obligations; do not raise timeouts or add elaborate instrumentation.
- **Correction limit.** After two unsuccessful corrections of one issue, try one simpler approach within scope. If unresolved, record the failure and request a human decision. Renaming the issue does not reset retries. A blocked change stops immediately under the checkpoint rule.
- **Audit scope.** Findings are spec clauses no test asserts. Test helper design, observer calibration, platforms, unnamed edge cases and these conventions are not findings. A re-audit may raise findings only for spec IDs that had findings in the previous round.
- **Audit rounds.** At most two audit-findings round trips per change, persisted by the controller. Further or untestable findings become Questions; let the controller block and release the claim, then stop for a human. Do not start a replacement change to reset this bound.
- **Wrong evals.** Use the controller's eval_fix kind to correct frozen evals under audit, preserving listed coverage and passing all own evals. Controller capabilities govern the build even before the NEW product implements that kind.
- **Authoring.** Motivation names a design/SYSTEM clause or user-visible need. Prefer narrowing an overbroad spec through an authorized change with already_satisfied over hardening beyond the design. Preserve design obligations and reuse existing assertions; no manual Spec/Decision edits. Batch related work within one module, with no numeric cap on affected spec items for any change kind. Keep changes coherent and reviewable and each spec atomic. Spec-only splitting and eval retargeting preserve every behavioral obligation and assertion and leave product behavior and public interfaces unchanged. D006 diagnostic migrations remain limited to existing error paths, eval corrections and explanations for emitted codes; preserve behavioral assertions and interfaces, and add no unsupported features or speculative errors. Normal verification, independent audits and checkpoint rules remain unchanged.
- **Human checkpoints.** Stop whenever a change blocks. There is no applied-change count, consecutive-module stop or separate checkpoint review; the product's P07 unapproved-work bound and audit rounds still apply. Read the live unapproved count from controller `status --json` and the limit from fireweed.yaml; never record either in planning documents. Record process notes in PROGRESS.md, not module Decisions. Never alter refs, bounds or requirements to evade enforcement.
- **Decisions.** Record only behavioral choices absent from the spec, each in one or two sentences. Fireweed appends these to SPEC.md for later workers/regeneration. Fixture, verification, recovery and process notes belong in Notes/PROGRESS.md. Drop stale or superseded choices through Removed decisions. Keep module Decisions under about 300 words.
- **Evidence.** The archived change's Provenance is the per-change record. Do not write separate report files, hash manifests or testcase inventories; update PROGRESS only when state, next work or standing rules change. Reuse valid setup, checks and drills; repeat only when relevant changes or unresolved failures invalidate evidence. Required controller phase checks still run.
- **Acceptance.** Use one focused design/inventory review, then review fixes only for affected requirements. Warnings need a scoped fix or a recorded explanation, not speculative cleanup. All existing gates must pass; once they do, stop verification unless later changes invalidate evidence. Drill gaps authorize no automatic follow-up changes.
